# PiPi: KISS onboarding через клиентского агента

9 сентября 2026 года. Рекомендуемый пересмотр [первоначального исследования](agent-assisted-onboarding-research.md).
Статус: реализация и независимая проверка сценариев в ветке `codex/agent-assisted-onboarding`.
Подключения проверяются в изолированных тестах; реальные пользовательские credentials
и фоновые службы этой рабочей машины для проверки не используются.

Первый пользователь — человек с Codex или Claude Code на своём компьютере,
который хочет личного Telegram-помощника и не умеет настраивать серверы.
Для первого PR целевой путь — локальный macOS/Linux, один владелец, один бот.
Удалённый сервер и дополнительные каналы не появляются в начальном выборе.

Обещание продукта: «Попросите своего агента установить PiPi. Подключите AI и Telegram.
Начните разговор». Это три понятных этапа, а не обещание трёх кликов: регистрация,
оплата провайдера и создание Telegram-бота могут потребовать дополнительных действий.

Стартовая личность тоже должна быть понятна: **PiPi начинает как Jeeves** — личный
помощник с тактичным тоном. Это отправная точка, которую владелец может менять:
попросить другой тон, добавить правила и факты о себе, выбрать другую специализацию.
Страница настройки и первое приветствие объясняют это простыми словами. Существующие
`/pack` и `/pack mutate <id>` дают явный путь смены установленной личности;
пожелания и правила сохраняются через контекст пространства. Повторный setup показывает
текущую личность и не возвращает изменённого PiPi к Jeeves. Для свежей установки нужен
нейтральный личный контекст без выдуманных сведений о владельце или его работе.

**Что меняем в предыдущем решении**

| Было предложено | Теперь рекомендуем | Причина |
| --- | --- | --- |
| Анкета и подготовка owner-spec до запуска | Первый полезный разговор, затем постепенное знакомство | Профиль не должен быть условием первой помощи. |
| Пользователь настраивает environment и owner IDs | Локальная страница подключения и одноразовая Telegram-ссылка | Технические идентификаторы получает программа. |
| Пять CLI subcommands, отдельные plan/apply-файлы | Один `pnpm setup`; существующий doctor для диагностики | У сценария одна точка входа и повторного запуска. |
| Ручной API key как основной путь | Кнопка входа через OpenRouter; вставка существующего ключа как запасной путь | OpenRouter уже является default provider PiPi; нет необходимости менять продуктовый выбор. |
| Фоновый запуск отложен | Явный выбор «Оставить работать в фоне» входит в завершение | Закрытие coding agent не должно неожиданно выключать ассистента. |
| Развёрнутая машина стадий с журналом каждой операции | Проверка фактической конфигурации и небольшой pending setup state | Продолжение нужно; отдельный workflow engine не нужен. |

**Сценарий на языке владельца**

1. **«Установи мне PiPi».** На странице проекта — один готовый текст для Codex/Claude
   со ссылкой на общий runbook. Клиентский агент проверяет окружение, устанавливает
   зависимости и открывает локальную страницу. Пользователь видит короткое сообщение
   о ходе работы и только те запросы, где действительно нужен его выбор.
2. **«Подключить AI».** Основная кнопка — «Подключить OpenRouter» с коротким объяснением,
   кто предоставляет модель и где оплачивается использование. Вход проходит на стороне
   провайдера; PiPi получает ключ непосредственно в локальном процессе. После возврата
   выполняется реальный запрос. При нехватке баланса показывается конкретное действие,
   а уже сделанная настройка сохраняется. Список моделей спрятан в дополнительные настройки.
3. **«Подключить Telegram».** Если у человека нет бота, показать ссылку на BotFather
   и короткие последовательные инструкции: создать бота, выбрать имя, скопировать
   выданный токен в приватное поле этой страницы. Проверить токен сразу и показать,
   какого бота подключили. Не просить прислать токен coding agent в чат.
4. **«Открыть моего PiPi».** Одноразовая ссылка открывает личный диалог. На странице
   настройки появляется найденный Telegram-аккаунт и кнопка «Это я». После подтверждения
   определяется owner; пользователь не ищет свой numeric ID и не редактирует allowlist.
5. **«С чего начнём?»** PiPi отвечает в Telegram. При отсутствии задачи предлагает
   короткие примеры: разобрать дела на сегодня, записать задачу, обсудить вопрос.
   Если задача уже была передана клиентским агентом, сразу работает над ней.
   Имя из Telegram, язык разговора и часовой пояс браузера служат исправляемыми
   предложениями. Недостающие сведения спрашиваются тогда, когда нужны для задачи.
6. **«Оставить работать в фоне».** После успешного ответа — понятный выбор фоновой
   работы и короткое объяснение, что PiPi работает на этом компьютере и недоступен
   во время его сна или выключения. Альтернатива — временно попробовать в текущем
   запуске. У каждого варианта явно указан срок работы; есть способ остановить PiPi.

Страница одна, следующий раздел раскрывается по мере готовности предыдущего.
На ней не нужны dashboard, модельный каталог, presets, packs, Docker, порты или JSON.
Вход, платежи и секретные поля выполняет сам владелец. Coding agent получает только
безопасные статусы; в его transcript не возвращаются ключи, OAuth-коды и body запросов.

**Что подтверждено источниками**

OpenRouter документирует OAuth PKCE с localhost callback на произвольном порту
и обменом кода на пользовательский ключ. Это делает предложенную кнопку подключения
реалистичной без собственного облачного посредника. У локального приложения на странице
авторизации отображается host/port; установщик должен заранее объяснить это владельцу.
Интеграция покрыта тестами с подставным провайдером; живой вход с пользовательским
аккаунтом не выполнялся.
[OpenRouter OAuth](https://openrouter.ai/docs/guides/overview/auth/oauth).

Telegram документирует передачу параметра через `/start` в deep link, а входящее
сообщение содержит данные отправителя. Из этого следует возможность самостоятельно
реализовать подтверждение аккаунта. Одноразовость, срок действия и проверку владельца
обеспечивает PiPi; Telegram не предоставляет их автоматически для любой ссылки.
[Telegram deep links](https://core.telegram.org/bots/features#deep-linking),
[Bot tutorial](https://core.telegram.org/bots/tutorial).

Публичные issues дают примеры проблем, но не измерение их распространённости:
в Hermes описана созданная конфигурация, после которой первый разговор ошибочно
запускается без готового провайдера; в OpenClaw — непонятный путь смены провайдера.
Это поддерживает решение проверять соединение сразу и возвращать человека в тот же
раздел настройки, не начинать всё заново.
[Hermes #94071](https://github.com/NousResearch/hermes-agent/issues/94071),
[OpenClaw #88373](https://github.com/openclaw/openclaw/issues/88373).

| Проблема | Приоритет для этого PR | Основание и уверенность |
| --- | --- | --- |
| Ручные ключи, ID и конфиги | Высокий | Наблюдается в текущем runbook PiPi; трудность для новичка — обоснованная гипотеза, пока без user-test. |
| «Готово» до рабочего ответа | Высокий | Doctor PiPi проверяет конфигурацию, не весь диалог; есть аналогичный публичный issue. |
| Бот исчезает после завершения установки | Высокий | Текущий native путь предлагает dev/start; пользовательское ожидание постоянной работы нужно проверить. |
| Длинная анкета и выбор моделей | Средний | Это недостаток нашего первого предложения, а не подтверждённая статистика отказов пользователей. |

**Минимум реализации под этим интерфейсом**

- Один standalone setup process с маленькой loopback-страницей; он работает до
  загрузки основного runtime, потому что runtime пока требует ключи и owner.
  Один общий сервис настройки обслуживает страницу и безопасные статусы для агента.
  `pnpm setup` при повторе обнаруживает готовые подключения и продолжает недостающие.
- Конфигурация только локально под `DATA_DIR`: отдельно несекретные настройки
  и credential-файл с ограниченным доступом владельца. Никакого нового vault-сервера,
  изменения `.env` или записи личных данных в `src/groundings`. Один resolver читает
  эти данные для setup, doctor и runtime; явно заданный env имеет приоритет.
  Файлы сохраняются атомарно, существующая установка не переписывается молча.
- OAuth S256 PKCE с привязкой callback к конкретной setup-сессии. Локальная страница
  доступна только через loopback; нужны проверка origin/host и защита управляющих
  запросов токеном сессии. Secret-bearing URL и тела запросов не логируются.
- Узкая owner-привязка: helper принимает только private `/start <nonce>` для текущего
  подключения, затем ждёт локальное «Это я». Nonce имеет срок действия и используется
  один раз. После сохранения owner helper прекращает polling до запуска runtime.
  Существующих owners он не заменяет. Не включать `BOOTSTRAP_OWNER_MODE` и не назначать
  владельцем первого случайного отправителя. Это новое поведение первоначальной
  привязки, его нужно явно рассмотреть в PR как изменение настройки доступа.
- Один владелец процесса: setup helper и runtime не должны одновременно получать
  Telegram updates. Занятый bot token, активный webhook или конфликт другого процесса
  возвращаются как понятная проблема подключения; чужой webhook не удаляется.
- Начальный режим использует один AI-доступ для текста и tool calls. Это нужно задать
  явно: текущий OpenRouter default PiPi отправляет tool calls в Gemini и требует второй
  ключ. Проверять и текст, и безвредный tool round-trip. Дополнительные возможности
  предлагать после их проверки, не выдавать неподключённый поиск/голос за готовые.
- Небольшая необязательная карточка от coding agent: до нескольких релевантных фактов
  и текущая задача. Владелец может исправить/отклонить её; отсутствие карточки не блокирует
  старт. Хранение через текущий контекст личного пространства. `/setup apply` не вызывать
  как финальный шаг: сейчас он сбрасывает pack и включает браузер/расписания.
- Фоновый запуск — явный пользовательский выбор и небольшой адаптер под поддержанную ОС,
  с проверкой единственного процесса, restart и stop. Корректно различать продолжение
  после закрытия coding agent, запуск после входа пользователя и работу при выключенном
  компьютере. Последнее локальная установка не обеспечивает.

Не нужен отдельный планировщик установки, набор файлов plan/apply или обязательная
генерация профиля второй LLM. Остаются валидация, отказ при конфликте, простое pending
состояние и безопасный JSON-результат doctor. Уменьшаем число механизмов, сохраняя
защиту от повторного запуска, потери настроек и неверной привязки аккаунта.

**Где следующий реальный скачок простоты**

Telegram теперь документирует Managed Bots: пользователь открывает ссылку создания,
подтверждает имя; management bot получает данные нового бота и создателя и может
запросить токен. Такой путь потенциально убирает BotFather-инструкцию и ручной перенос
токена. Но для PiPi он потребует работающего manager bot и проверенной передачи credential
конкретной локальной установке. Это отдельный сервис с доступом к bot tokens, а не
бесплатное упрощение локального installer. Рекомендация: проверить отдельным экспериментом
после первого локального сценария, не делать обязательной зависимостью первого PR.
[Telegram Managed Bots](https://core.telegram.org/bots/features#managed-bots).

**Когда можно назвать путь простым**

Техническая приёмка: одинаковая конфигурация у doctor и runtime; валидный текстовый
и инструментальный запрос; корректный owner-check; реальный ответ в личном Telegram;
повтор setup без дублей; восстановление после отмены входа; отсутствие секретов в
агентном отчёте; поддержанный фоновый запуск переживает закрытие coding agent.
Для изменения поведения нужны тесты и `pnpm verify`, плюс отдельная проверка жизненного
цикла на каждой заявленной ОС. Производственные токены и конфигурация для тестов не нужны.

UX-проверка перед обещаниями: дать 3–5 новичкам только стартовую инструкцию и наблюдать,
где они просят помощи. Это небольшой качественный тест, не статистика рынка.
Фиксировать первый полезный ответ, лишние вопросы, возвраты между окнами и понимание
того, где работает бот и кто оплачивает AI. Успех: никто не редактирует файлы,
не ищет Telegram ID и не пытается вставить секрет в чат с coding agent.

Сквозная приёмка реализации проверяет локальный путь
«вход OpenRouter → Telegram-подключение → owner → первый ответ → фоновая работа»
через действующий интерфейс настройки с подставными провайдерами и runtime.

Код включает настройку первоначального владельца и управление фоновым запуском
по его явному выбору. Тесты не означают установку служб или изменение production;
`.env` рабочей копии не редактируется.
