# Настройка Open PiPi внешним coding agent

Исследование от 9 сентября 2026 года. Статус: проект отдельного PR, без реализации.
После повторного разбора для неопытного пользователя рекомендуемый сценарий и
объём реализации перенесены в [KISS-проект](agent-assisted-onboarding-kiss.md).
Он заменяет первоначальные предложения ниже об анкете, ручном owner allowlist,
пяти командах setup и исключении фонового запуска. Сравнение источников сохраняется.
Локальная база: Open PiPi `fb13132` (`v2.9.0`). Исследование первоисточников
выполнено с тремя параллельными Terra-субагентами: OpenClaw; Hermes;
NanoClaw, nanobot и ZeroClaw. Выводы сопоставлены с исходниками PiPi.

Цель: владелец просит Codex, Claude Code или другого coding agent настроить PiPi;
агент устанавливает зависимости, собирает нужные предпочтения, применяет настройки,
проверяет работу и передаёт владельцу персонального Telegram-ассистента.
Создание учётных данных и приватный ввод секретов остаются действиями владельца.

Рекомендация: дать внешнему агенту небольшой общий runbook и детерминированный CLI.
Беседу и подготовку профиля ведёт coding agent; проверку входных данных,
запись состояния и доказательства готовности обеспечивает сам PiPi.

Это анализ документации и кода, а не сравнительный прогон установщиков.
Ссылки на `main`/`master` и страницы документации изменяемые: перед реализацией
заимствуемых деталей нужно повторно сверить конкретный контракт.

**Детали, которые меняют проектирование**

- В OpenClaw `--json` не означает `--non-interactive`. Пропуск health-check
  допускает конфигурацию без доступного Gateway. Следовательно, успешный exit code
  не заменяет проверку конечного результата. Режим SecretRef позволяет сохранять
  ссылки на секреты вместо значений в обычной конфигурации.
  [CLI automation](https://docs.openclaw.ai/start/wizard-cli-automation).
- OpenClaw отдельно проводит первый разговор об идентичности и сохраняет её;
  bootstrap рассчитан на однократное прохождение. Это полезный образец передачи
  ассистента владельцу после технической установки.
  [Agent bootstrapping](https://docs.openclaw.ai/start/bootstrapping).
- У Hermes есть существенное ограничение: текущий `setup.py` при отсутствии TTY
  или `--non-interactive` печатает инструкции и возвращается, не выполняя мастер.
  До этого возможны создание home и backup config; `--reset` применяется ещё раньше.
  Поэтому этот режим нельзя считать ни полноценным unattended setup, ни dry-run.
  [Исходник setup.py](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/hermes_cli/setup.py).
- Hermes явно различает `SOUL.md` (идентичность), `USER.md` (профиль владельца),
  `MEMORY.md` (накопленные факты) и проектные инструкции. Для PiPi полезна эта
  семантика; копировать имена файлов или создавать вторую систему памяти не требуется.
  [Which File Does What?](https://hermes-agent.nousresearch.com/docs/user-guide/which-file-does-what).
- Старые материалы NanoClaw описывают длинный Claude setup-skill. Актуальный
  репозиторий находится в `nanocoai/nanoclaw`, и текущий skill существенно короче.
  Установщик разделяет краткий пользовательский статус, журнал шагов и полные логи.
  Это полезнее для повторяемости, чем длинный список свободных shell-инструкций.
  [Репозиторий](https://github.com/nanocoai/nanoclaw),
  [установщик](https://raw.githubusercontent.com/nanocoai/nanoclaw/main/nanoclaw.sh).
- Привязка канала и установление владельца — разные факты. У OpenClaw есть pairing,
  Hermes документирует числовой Telegram user ID и allowlist. В PiPi для первого PR
  следует использовать существующую проверку владельца, сохранив отказ неизвестным
  пользователям. Новый pairing-протокол не нужен для этой задачи.
  [OpenClaw pairing](https://docs.openclaw.ai/channels/pairing),
  [Hermes Telegram](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/telegram).

**Предлагаемый сценарий владельца**

1. Владелец просит: «Установи и настрой мне PiPi для Telegram».
   Coding agent читает общий runbook, проверяет окружение и устанавливает зависимости.
2. Короткая беседа: как обращаться, язык и часовой пояс, для чего нужен PiPi,
   предпочтения общения и первая задача. Уже известные релевантные сведения агент
   собирает в короткую карточку для проверки владельцем. Неизвестное оставляет пустым.
3. Владелец выбирает доступного провайдера и приватно предоставляет учётные данные.
   Агент видит только наличие/результат проверки. В первом PR используется текущий
   operator-managed environment; `.env` агент не читает и не редактирует.
4. Агент применяет проверенный несекретный план и проверяет ответ модели.
   Запуск выполняется в рамках явно запрошенного режима; установка фонового сервиса
   остаётся отдельным выбором. При прерывании сценарий продолжается с текущего состояния.
5. Владелец открывает бота и пишет ему. PiPi проверяет существующий owner allowlist,
   применяет подготовленный профиль к его личному пространству и продолжает разговор
   с уже известными предпочтениями.
6. PiPi выполняет одну согласованную полезную задачу. Coding agent получает безопасный
   результат проверки и сообщает, что настроено, что реально проверено и как продолжить.

Профиль, подготовленный coding agent, содержит только выбранные для передачи факты.
Полные истории Codex/Claude, проектные инструкции и credential-файлы не импортируются.
Личные сведения владельца первоначально привязываются к личному пространству;
перенос в семейный или командный чат требует явного выбора аудитории.

**Предлагаемый контракт CLI — этих команд пока нет**

Сохранить существующий `pnpm setup:check -- --json`. Для управления сценарием
предлагается один новый entrypoint; конкретное имя окончательно выбрать при реализации:

```text
pnpm setup:agent -- inspect --json
pnpm setup:agent -- plan --input data/setup/owner-spec.json --json
pnpm setup:agent -- apply --plan data/setup/plan.json --json
pnpm setup:agent -- verify --live --json
pnpm setup:agent -- status --json
```

`inspect` и `plan` не создают runtime state, не открывают БД на запись и не вызывают
провайдеров. Сохранение файла плана — явная операция вызывающего клиента.
`apply` проверяет актуальность плана и меняет только перечисленные настройки.
`verify --live` выполняет ограниченные сетевые проверки в согласованном режиме.
Повторный `apply` того же плана — no-op; конфликт с последующими изменениями
владельца возвращается как конфликт, а не разрешается перезаписью.

В stdout — один JSON-объект с `schemaVersion`, `status`, `checks`, `changes`,
`nextActions`. Диагностика идёт в stderr и очищается от секретов. Статусы
`needs_owner`, `conflict`, `failed`, `complete` различаются; таблица exit codes
публикуется и проверяется тестами. Человекочитаемый текст не является протоколом.

Прогресс хранится отдельно от `onboarding_state`, например в локальном JSON-журнале
под `DATA_DIR/setup/`. Для первого PR новые таблицы и миграции не требуются.
Факты готовности могут быть независимыми: `config_valid`, `profile_prepared`,
`model_verified`, `runtime_running`, `owner_seen`, `profile_applied`, `first_action_verified`.
У каждого факта есть время и привязка к версии конфигурации; смена провайдера,
токена, профиля или runtime делает связанные старые проверки неактуальными.
Значения секретов в журнал не попадают.

Успешный Telegram `getMe` подтверждает bot token, но не диалог владельца.
Отправка в очередь не равна доставке. Завершение handoff требует входящего сообщения
ожидаемого владельца, ответа с применённым профилем и подтверждённого результата
первой задачи. Проверка модели и задачи ограничена временем и числом запросов.

**Объём отдельного PR**

- Общая инструкция для клиентских агентов с короткими входами из `AGENTS.md`
  и `CLAUDE.md`; одинаковый CLI для обоих клиентов. Новые SDK или MCP-сервер не нужны.
- Версионированная схема несекретного setup-spec: предпочтения, выбранные доступные
  provider/model/pack, первая задача. Никаких произвольных shell-команд или секретов.
  Owner allowlist остаётся operator-managed; профиль не может назначать права.
- Общий resolver для allowlisted несекретной конфигурации и environment, используемый
  doctor и runtime. Существующее явно заданное environment имеет приоритет;
  конфликт с предложенным планом виден до записи. Нельзя только сохранить JSON,
  который runtime затем не прочитает.
- Planner, apply, журнал продолжения и ограниченная live verification.
  По умолчанию native Node/pnpm и один Telegram-канал.
- Однократная передача профиля в существующий контекст личного пространства
  после owner-check. Предпочтительны текущие grounding overrides и space preferences.
  Для полей без соответствия в текущей модели нужен один явный способ чтения runtime.
  Снимки и их refresh не должны терять применённую персонализацию.
- `/setup` отражает подготовленный профиль и оставшиеся шаги; повторная обработка
  не включает расписания, не меняет pack и не перезаписывает последующие правки.

Docker, cloud deploy, автоматическая установка system service, новый secret vault,
импорт истории других агентов, новые права доступа и переписывание памяти
в этот PR не входят. Это сохраняет задачу в пределах native Telegram onboarding.

**Критерии приёмки и проверки реализации**

| Сценарий | Требуемый результат |
| --- | --- |
| Запуск без TTY | Не зависает на вопросах; возвращает валидный JSON и нужные действия владельца. |
| Чистое окружение без ключей | Можно подготовить и проверить профиль; нет обязательного LLM-вызова при персонализации. |
| Ошибка schema, timezone, ID или путь вне разрешённого каталога | Отказ до любых записей; тестировать также symlink и `..`. |
| Повтор после прерывания | Сохраняются готовые шаги; нет дубликатов профиля, задач и сообщений. |
| Изменённый после plan config | `conflict`; существующие значения не теряются. |
| Невалидный ключ или недоступный provider | `config_valid` не превращается в `model_verified`; понятная безопасная ошибка. |
| Посторонний Telegram-пользователь | Не получает владельца, его профиль или доступ через bootstrap mode. |
| Выбранный профиль и pack | Первый диалог использует их; defaults не сбрасывают выбор. |
| Уже работающий бот | Не создаётся второй polling process; результат привязан к нужной установке. |
| Секреты в ошибках SDK/HTTP | Не попадают в stdout, stderr, журнал, профиль и тестовые артефакты. |
| Первый результат | Есть подтверждённый входящий owner turn и доставленный ответ, а не только `/health`. |

Unit/integration проверки выполняются с синтетическими данными, подменёнными
провайдерами и изолированным `DATA_DIR`. Для реализации обязателен `pnpm verify`;
ручная проверка — один и тот же сценарий через Codex и Claude Code на тестовом боте.

Исследовательский этап изменяет только этот документ. Runtime, зависимости,
`.env`, production-конфигурация и базы данных не изменялись. Основные риски будущей
реализации: рассогласование resolver/doctor/runtime, повторная запись после сбоя,
утечка личного профиля в общий чат, сброс настроек defaults и ложное сообщение
«готово» по устаревшей или неполной проверке.
